# DocFlow — бэкенд распознавания документов и выгрузки в 1С

Сервис принимает фото и сканы документов, распознаёт тип документа и извлекает
реквизиты, показывает результат оператору на проверку и после подтверждения
выгружает данные в 1С. Всё распознавание выполняется локально: OCR через
Tesseract плюс локальная LLM для сложных случаев. Внешние облака и сторонние
Vision/GPT-сервисы не используются — данные не покидают сервер заказчика.

## Стек

- Go 1.22, стандартная библиотека + минимум зависимостей (`lib/pq`, `golang-jwt`, `google/uuid`)
- PostgreSQL для метаданных, очереди распознавания и очереди выгрузки
- Файлы на диске, зашифрованы AES-256-GCM
- OCR: `tesseract` (+ `pdftoppm`, `convert` для подготовки страниц)
- LLM: любой OpenAI-совместимый локальный сервер (например, llama.cpp)

Внешних вызовов в интернет нет. CGO не используется — бинарник статический.

## Как работает распознавание

1. Файл расшифровывается во временный каталог.
2. PDF растеризуется в PNG (`pdftoppm`), изображения нормализуются (`convert`).
3. Tesseract извлекает текст (`rus+eng`).
4. По тексту работают правила: определяется тип документа (счёт-фактура, УПД,
   накладная, акт, договор, чек и т.д.) и извлекаются реквизиты
   (дата, сумма, №, ИНН, КПП, контрагент) через регулярные выражения.
5. Если уверенность правил низкая или тип не определён — подключается локальная
   LLM, которая структурирует текст в строгий JSON. Её поля приоритетнее.
6. Документ переходит в статус `needs_review`. Оператор проверяет и правит.

Список типов документов не зашит жёстко: новый тип добавляется правилом в
`internal/recognize/classify.go`, а LLM обрабатывает всё остальное.

## Статусы документа

`received → processing → needs_review → confirmed → exported`
(`failed` — при ошибке распознавания; выгрузка ретраится с backoff).

При включённой автовыгрузке (`AUTO_EXPORT_ENABLED=true`) маршрут короче:
полностью распознанный документ идёт `received → processing → confirmed → exported`
без оператора, а при нехватке полей — `… → needs_input → (клиент дозаполняет) →
confirmed → exported`. Подробнее — раздел «Автовыгрузка».

## HTTP API

Аутентификация — JWT в заголовке `Authorization: Bearer <token>`.

| Метод | Путь | Роль | Назначение |
|-------|------|------|-----------|
| POST | `/api/auth/login` | — | Логин, выдаёт токен |
| POST | `/api/documents` | все | Загрузка файла (multipart, поле `file`) |
| GET | `/api/documents` | все | Список (клиент видит только свои) |
| GET | `/api/documents/{id}` | все | Карточка документа |
| GET | `/api/documents/{id}/file` | все | Скачать оригинал |
| PATCH | `/api/documents/{id}` | оператор/админ | Правка типа и реквизитов |
| POST | `/api/documents/{id}/confirm` | оператор/админ | Подтвердить → в очередь на 1С |
| POST | `/api/documents/{id}/complete` | клиент(свои)/оператор/админ | Дозаполнить недостающие поля → досыл в 1С |
| POST | `/api/documents/{id}/reprocess` | оператор/админ | Повторное распознавание |
| POST | `/api/devices` | все | Регистрация push-токена устройства |
| DELETE | `/api/devices` | все | Отвязка push-токена (при выходе) |
| POST | `/api/users` | админ | Создать пользователя |
| GET | `/api/users` | админ | Список пользователей |
| GET | `/api/audit` | админ | Журнал действий |
| GET | `/healthz` | — | Проверка живости и БД |

## Интеграция с 1С

Режим задаётся `ONEC_MODE`:

- `file` — EnterpriseData XML пишется в каталог `ONEC_FILE_DIR`, откуда его
  забирает 1С (файловый обмен).
- `rest` — POST JSON на HTTP-сервис 1С (`ONEC_REST_URL`, опционально
  `ONEC_AUTH_HEADER` вида `Имя: значение`).
- `disabled` — выгрузка отключена.

Если 1С недоступна, задание остаётся в очереди и повторяется с нарастающей
задержкой до `ONEC_MAX_ATTEMPTS` попыток.

## Автовыгрузка и частичное распознавание

Управляется `AUTO_EXPORT_ENABLED` (по умолчанию `true`):

- **Всё распознано** (тип определён, все обязательные реквизиты на месте) — документ
  подтверждается автоматически и уходит в 1С без участия оператора.
- **Часть полей не распознана** — распознанное отправляется в 1С сразу (частичная
  выгрузка, `kind=partial`, признак `incomplete`), документ переходит в `needs_input`,
  а клиент получает уведомление и вводит недостающие поля вручную. После этого идёт
  досыл (`kind=update`) к тому же документу — 1С сопоставляет его по `SourceId`
  (upsert). Обязательные поля задаются по типу документа в
  `internal/recognize/required.go`.
- **Тип не определён** — документ идёт на проверку оператору (`needs_review`), как и при
  выключенной автовыгрузке.

Все три вида выгрузки (`create` / `partial` / `update`) несут стабильный `SourceId`,
поэтому 1С обновляет одну и ту же запись, а не плодит дубли.

## Push-уведомления

Серверные уведомления о смене статуса (`принят / распознан / нужно уточнение /
ушёл в 1С / ошибка`) отправляются на устройства пользователя: Android — через FCM
HTTP v1, iOS — через APNs (token-based, ключ `.p8`). Токены регистрируются
приложением через `POST /api/devices` и хранятся в таблице `device_tokens`;
невалидные токены удаляются автоматически при доставке.

Включается `PUSH_ENABLED=true` и заполнением ключей провайдеров (см. `.env.example`).
Наружу уходит только факт смены статуса и имя документа — не содержимое и не
распознанные данные. Если push выключен, приложение показывает локальные
уведомления по опросу статуса, так что мобильный клиент работает и без него.

## Запуск через Docker

```bash
cp .env.example .env
# заполнить JWT_SECRET и FILES_ENCRYPTION_KEY:
#   openssl rand -hex 32
docker compose up -d --build
```

При первом старте с пустой базой создаётся администратор. Если
`BOOTSTRAP_ADMIN_PASSWORD` не задан, пароль генерируется и один раз пишется в лог
(`docker compose logs app`).

## Запуск на сервере без Docker

Нужны установленные бинарники:

```bash
apt-get install -y tesseract-ocr tesseract-ocr-rus tesseract-ocr-eng \
                   poppler-utils imagemagick
```

Собрать и запустить:

```bash
go build -o docflow ./cmd/server
export $(grep -v '^#' .env | xargs)
./docflow
```

## Локальная LLM

Подойдёт llama.cpp с небольшой квантованной моделью на CPU, например
Qwen2.5-7B-Instruct (Q4_K_M). Запуск сервера:

```bash
llama-server -m qwen2.5-7b-instruct-q4_k_m.gguf --host 0.0.0.0 --port 8081 -c 4096
```

и `LLM_BASE_URL=http://127.0.0.1:8081/v1`. Если LLM не нужна на старте —
`LLM_ENABLED=false`, распознавание останется на правилах и OCR.

## Структура

```
cmd/server         точка входа, миграции, воркеры, graceful shutdown
internal/config    конфиг из переменных окружения
internal/domain    доменные модели и статусы
internal/storage   PostgreSQL, миграции, очереди (SKIP LOCKED)
internal/auth      PBKDF2-хэши паролей, JWT
internal/filestore шифрование файлов на диске (AES-256-GCM)
internal/recognize OCR, подготовка страниц, правила, LLM, пайплайн
internal/onec      выгрузка в 1С (file / rest)
internal/worker    фоновые воркеры распознавания и выгрузки
internal/httpapi   HTTP-роуты, middleware, хендлеры
```

## Безопасность

Файлы шифруются на диске, пароли хранятся как PBKDF2-HMAC-SHA256, доступ
разграничен по ролям (client / operator / admin), действия пишутся в журнал
аудита. Рекомендуется поднимать сервис за HTTPS-реверс-прокси (nginx/Caddy) и
включать TLS у PostgreSQL в проде.
