# Мобильное приложение (Capacitor)

Обёртка над сайтом: те же экраны + нативные куски поверх — съёмка камерой,
правка фото (обрезка/поворот/контраст/яркость), оффлайн-очередь (IndexedDB) и
серверные push-уведомления о смене статуса документа.

Нативные проекты **лежат в репозитории**: `docflow-frontend/android` и
`docflow-frontend/ios`. В них уже прописаны разрешения, идентификатор
приложения, версии и минимальные версии ОС — пересоздавать их через `cap add`
не нужно и не следует (это затрёт настройки).

| Параметр | Значение |
|---|---|
| App ID (bundle id) | `by.docflow.app` |
| Отображаемое имя | DocFlow |
| Версия | `1.0.0` (versionCode 1) |
| Android минимум | 8.0 (API 26) — ТЗ §3 |
| iOS минимум | 14.0 — ТЗ §3 |

> App ID зафиксирован до первой публикации. После выкладки в сторы он не
> меняется, поэтому если заказчик хочет свой обратный домен
> (например `by.klient.docflow`) — менять нужно **сейчас**, до сборки:
> `capacitor.config.json` + `applicationId` в `android/app/build.gradle` +
> bundle id в Xcode.

## Сборка

```bash
cd docflow-frontend
npm install

# Адрес сервера заказчика: из приложения относительные /api не работают.
echo 'VITE_API_BASE_URL=https://docs.klient.by' > .env.local

npm run cap:sync            # build + копирование web-ассетов в android/ и ios/
npm run cap:android         # откроет Android Studio
npm run cap:ios             # откроет Xcode (только macOS)
```

Что нужно на машине сборки: Node 18+, JDK 17 и Android Studio (Android);
Xcode 15+ и CocoaPods (iOS, только macOS). Бэкенд и распознавание при этом
остаются на сервере заказчика — мобильная сборка к ним только обращается.

Разрешения уже прописаны:

* Android — `CAMERA`, `READ_MEDIA_IMAGES` (и `READ_EXTERNAL_STORAGE` для
  Android ≤12), `POST_NOTIFICATIONS`, `INTERNET`, `ACCESS_NETWORK_STATE`;
* iOS — `NSCameraUsageDescription`, `NSPhotoLibraryUsageDescription`,
  `NSPhotoLibraryAddUsageDescription` (тексты на русском, их увидит ревьюер).

## Подпись релиза

**Android.** Ключ хранится у заказчика, в репозиторий не попадает
(`.gitignore` исключает `*.keystore` и `keystore.properties`).

```bash
keytool -genkey -v -keystore docflow-release.keystore \
  -alias docflow -keyalg RSA -keysize 2048 -validity 10000
```

`android/keystore.properties` (создаётся локально на машине сборки):

```properties
storeFile=/absolute/path/docflow-release.keystore
storePassword=…
keyAlias=docflow
keyPassword=…
```

Потеря ключа = невозможность обновить уже опубликованное приложение. Ключ и
пароли передаются заказчику вместе с остальными секретами (см. README-DEPLOY,
раздел «Передача секретов»).

**iOS.** Сертификат распространения и provisioning profile выпускаются в
аккаунте Apple Developer **заказчика** — приложение работает с его
персональными данными, аккаунт подрядчика для этого использовать нельзя.

## Публикация (ТЗ §9)

Заказчик выбирает один из двух путей — решение нужно зафиксировать письменно
до сборки релиза, потому что от него зависят требования к аккаунтам:

1. **Публичные сторы.** Google Play + App Store. Понадобится: аккаунт
   разработчика заказчика (Google Play — разовый взнос, Apple — годовой),
   политика конфиденциальности на домене заказчика, заполненная форма
   Data Safety / App Privacy (передаются фото документов и реквизиты — это
   нужно указать честно), скриншоты и описание. Ревью Apple занимает обычно
   несколько дней, и первая подача нередко уходит на доработку.
2. **Закрытое корпоративное распространение.** Google Play (закрытое
   тестирование / Managed Google Play) и Apple Business Manager с Custom App.
   Быстрее и без публичного ревью, подходит, если приложением пользуются
   только клиенты заказчика.

В обоих случаях нужна опубликованная политика конфиденциальности, ссылающаяся
на инфраструктуру заказчика (см. README-DEPLOY, раздел «Персональные данные»).

## Push-уведомления (FCM + APNs)

Приложение при входе регистрирует токен устройства (`POST /api/devices`), а
сервер шлёт уведомления при смене статуса. Чтобы включить, на бэкенде
выставьте `PUSH_ENABLED=true` и заполните ключи в `.env`:

**Android (FCM):**
1. Создайте проект Firebase, добавьте Android-приложение с applicationId
   `by.docflow.app`, скачайте `google-services.json` в `android/app/`.
2. В Firebase → Project settings → Service accounts сгенерируйте приватный
   ключ (JSON), положите его на сервер и укажите путь в `FCM_CREDENTIALS_FILE`,
   а `FCM_PROJECT_ID` — id проекта.

**iOS (APNs):**
1. В Apple Developer создайте APNs Auth Key (`.p8`), запомните Key ID и Team ID.
2. Положите `.p8` на сервер и укажите `APNS_KEY_FILE`, `APNS_KEY_ID`,
   `APNS_TEAM_ID`, `APNS_TOPIC=by.docflow.app`. Для боевой сборки
   `APNS_PRODUCTION=true`, для отладки через Xcode — `false`.

После правок в `.env` — `./deploy.sh restart`. Наружу (в Google/Apple) уходит
только факт смены статуса и имя документа, без содержимого и распознанных
данных. Если push не включать, приложение показывает локальные уведомления по
опросу статуса.

## Камера и правка фото

Кнопка «Снять камерой» вызывает нативную камеру через `@capacitor/camera`; в
браузере — обычный `<input capture>`. Любое фото (JPG/PNG) перед отправкой
можно открыть кнопкой «Изменить»: обрезать выделением, повернуть, подстроить
контраст и яркость. Всё делается локально на устройстве, на сервер уходит уже
обработанный кадр.

## Открытый вопрос

Вход по SMS-коду (ТЗ §3 — «нужно уточнить, что удобнее») **не реализован**:
сейчас логин/пароль. SMS требует выбора провайдера рассылки и его оплаты
заказчиком, поэтому вынесен за периметр текущей поставки до отдельного решения.
