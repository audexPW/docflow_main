# DocFlow — развёртывание на сервере

Распознавание документов + выгрузка в 1С. Всё локально, без внешних облаков.
Стек: PostgreSQL + Go-бэкенд (OCR/правила/LLM) + React-фронт за nginx.

## Быстрый старт (одна команда)

Нужен только **Docker** с плагином **compose**. На чистой Ubuntu:

```bash
curl -fsSL https://get.docker.com | sh
```

Дальше — распаковать архив и запустить:

```bash
tar -xzf docflow-deploy.tar.gz
cd docflow-deploy
./deploy.sh
```

Скрипт сам:
- создаст `.env` и сгенерит секреты (JWT, ключ шифрования файлов, пароль админа);
- соберёт образы и поднимет контейнеры;
- дождётся `/healthz` и покажет адрес + логин/пароль администратора.

После этого веб-интерфейс доступен на `http://<IP-сервера>/` (порт задаётся
`HTTP_PORT` в `.env`, по умолчанию 80).

## Управление

```bash
./deploy.sh up        # пересобрать и поднять (после обновления кода)
./deploy.sh logs      # логи всех сервисов
./deploy.sh ps        # статус контейнеров
./deploy.sh restart   # перезапуск без пересборки
./deploy.sh down      # остановить (данные в volume'ах сохраняются)
./deploy.sh nuke      # снести контейнеры и volume'ы (ОСТОРОЖНО — удалит БД и файлы)
```

## Что учесть в проде

- **HTTPS.** Контейнеры слушают HTTP. Терминируйте TLS на внешнем nginx/Caddy
  перед `HTTP_PORT` (сертификат — Let's Encrypt/certbot). ТЗ требует HTTPS с телефона/браузера.
- **1С.** По умолчанию `ONEC_MODE=file` — бэкенд пишет EnterpriseData XML в volume
  `docflow_files` (`/var/lib/docflow/onec_outbox`), 1С забирает файлы. Для прямого
  обмена — `ONEC_MODE=rest` + `ONEC_REST_URL`/`ONEC_AUTH_HEADER` в `.env`, затем `./deploy.sh restart`.
- **OCR и LLM.** Базовая конфигурация — tesseract + правила, лёгкая по RAM.
  На стенде заказчика включены оба тяжёлых компонента, в `.env`:
  `COMPOSE_PROFILES=ai,ai-surya`, `OCR_ENGINE=surya`, `LLM_ENABLED=true`,
  `OCR_TIMEOUT=600s`. Surya поднимается сервисом `surya-ocr` (профиль
  `ai-surya`), llama.cpp — сервисом `llm` (профиль `ai`); профили независимы,
  и при `COMPOSE_PROFILES=ai-surya` LLM не поднимется. Всё на CPU, без интернета.

  Модель в репозиторий не входит: `.gguf` кладётся в `./models`, имя — в
  `LLM_GGUF`. Сейчас `Qwen2.5-7B-Instruct-Q4_K_M.gguf` (~4.4 ГБ, `LLM_THREADS=6`,
  `LLM_MEM_LIMIT=8g`). Без файла модели сервис `llm` уходит в цикл рестарта.
  Скорость на этом железе: ~50 ток/с на промпте, ~8 ток/с на генерации,
  порядка 1-2 минут на документ.

- **Бэкапы.** Есть готовые скрипты — см. раздел «Резервное копирование» ниже.
- **Шифрование БД на диске.** Файлы уже шифруются AES-256-GCM. Для БД включите
  TLS/шифрование тома средствами хоста — см. раздел «Персональные данные».

## Резервное копирование (ТЗ §7)

Три скрипта: снять копию, проверить её, восстановиться из неё.

```bash
./backup.sh                          # копия в ./backups/<UTC-штамп>
./backup.sh /mnt/nas/docflow         # копия в другой каталог
./verify-backup.sh backups/2026…Z    # ПРОВЕРКА восстановимости (ничего не ломает)
./restore.sh backups/2026…Z          # боевое восстановление (разрушающее)
```

В копию входят дамп PostgreSQL (`db.dump`), архив файлов документов
(`files.tar.gz`) и `manifest.txt` с контрольными суммами.

**Ключ шифрования в копию НЕ включён — и это осознанно.** Иначе одна украденная
копия давала бы и шифротекст, и ключ к нему. `FILES_ENCRYPTION_KEY` из `.env`
хранится отдельно (см. «Передача секретов»). Без него файлы из копии
восстановить невозможно — совсем, никаким способом.

### Проверка восстановимости

ТЗ требует не просто бэкапы, а подтверждение, что из них реально можно
восстановиться. `verify-backup.sh` делает это автоматически и не трогает боевой
стенд: поднимает одноразовый PostgreSQL, восстанавливает в него дамп,
распаковывает файлы во временный каталог и сверяет каждый документ —
файл на месте, расшифровывается текущим ключом, sha256 совпадает с записанной
в базе. Код возврата 0 = копия рабочая.

Именно последняя проверка ловит самый неприятный сценарий: база
восстановилась, файлы распаковались, а ключ не тот — формально «всё
восстановилось», фактически документы нечитаемы.

### Расписание

```cron
# ежедневная копия в 02:30
30 2 * * *  cd /opt/docflow-deploy && ./backup.sh >> /var/log/docflow-backup.log 2>&1

# еженедельная проверка восстановимости последней копии, воскресенье 03:30
30 3 * * 0  cd /opt/docflow-deploy && ./verify-backup.sh "$(ls -1d backups/*/ | tail -1)" >> /var/log/docflow-verify.log 2>&1
```

Глубина хранения — `BACKUP_KEEP_DAYS` (по умолчанию 30 дней). Копии лежат на том
же сервере, поэтому дополнительно отвозите их на отдельный носитель или в
хранилище заказчика: копия на том же диске не спасает от отказа диска.

## Передача секретов

При сдаче заказчику передаются отдельно от репозитория и от бэкапов:

| Секрет | Где | Что будет при потере |
|---|---|---|
| `FILES_ENCRYPTION_KEY` | `.env` | все документы **безвозвратно** нечитаемы |
| `JWT_SECRET` | `.env` | потребуется повторный вход всех пользователей |
| `POSTGRES_PASSWORD` | `.env` | доступ к базе только через контейнер |
| пароль администратора | выдан `deploy.sh` при первом запуске | вход в админку |
| ключ подписи Android (`.keystore`) | у заказчика | нельзя обновить приложение в Google Play |

`FILES_ENCRYPTION_KEY` — единственный секрет, потеря которого невосстановима.
Заказчику нужно хранить его в своём менеджере паролей и в бумажной копии в
сейфе. Проверить, что копия ключа рабочая, можно тем же `verify-backup.sh`.

## Персональные данные

Заказчик в Беларуси, поэтому применяется **Закон Республики Беларусь
от 07.05.2021 № 99-З «О защите персональных данных»** (не 152-ФЗ — это
российский закон, он здесь неприменим, если у заказчика нет обработки данных
российских субъектов).

Что уже сделано в системе: данные и файлы не покидают инфраструктуру заказчика,
файлы шифруются AES-256-GCM, доступ разделён по ролям, действия пишутся в
журнал (`audit_log`), пароли хранятся в виде PBKDF2-SHA256.

Что остаётся на стороне заказчика как оператора данных:

- назначить ответственного за внутренний контроль обработки перс. данных;
- уведомить субъектов и получить согласие на обработку;
- утвердить политику обработки и опубликовать её (она же понадобится для
  публикации мобильного приложения — см. `MOBILE.md`);
- определить срок хранения документов и порядок их удаления;
- включить шифрование тома с базой средствами хоста (LUKS или аналог).

Юридическую оценку соответствия даёт юрист заказчика — здесь описано только
техническое состояние системы.

## Структура

```
docflow-deploy/
├── deploy.sh              ← запуск в одну команду (секреты, HTTPS, профили)
├── smoke-test.sh          ← проверка сценариев приёмки
├── ACCEPTANCE.md          ← чеклист приёмки и границы поставки
├── Caddyfile              ← HTTPS, сертификат выпускается автоматически
├── backup.sh              ← резервное копирование
├── verify-backup.sh       ← проверка восстановимости копии
├── restore.sh             ← восстановление из копии
├── docker-compose.yml     ← оркестратор (db + backend + frontend + профили ai, ai-surya)
├── .env.example           ← шаблон конфига (deploy.sh делает из него .env)
├── docflow/               ← бэкенд (Go)
├── docflow-frontend/      ← фронт (React/Vite + nginx, обёртка Capacitor)
├── surya-ocr/             ← python-сервис OCR: Surya (профиль ai-surya)
└── backups/               ← сюда backup.sh складывает копии
```

## Интеграция с 1С (Беларусь)

Заказчик на «Моя бухгалтерия 8» (hs.by), Беларусь — в `.env` стоит `LOCALE=by`
(налоговый идентификатор УНП, 9 цифр). Формат выгрузки, соответствие полей
реквизитам 1С и задачи для 1С-специалиста описаны в `ONEC-INTEGRATION.md`,
готовые примеры XML — в папке `onec-samples/`.
