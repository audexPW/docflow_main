# Интеграция DocFlow → 1С: ТЗ для 1С-специалиста

Документ для разработчика 1С заказчика. Описывает формат выгрузки из DocFlow и
что нужно сделать на стороне 1С, чтобы распознанные документы попадали в базу.

## Контекст

- Конфигурация: **«Моя бухгалтерия 8»** (hs.by), платформа 1С:Предприятие 8.3, база файловая.
- Конфигурация **типовая, на поддержке** («Объект поставщика не редактируется»).
  Поэтому приёмник реализуется **расширением конфигурации**, а не правкой типовой —
  чтобы обновления вендора не затирали доработку.
- Страна — **Беларусь**: контрагент идентифицируется по **УНП** (9 цифр), не по ИНН.
- Обмен — **файловый**: DocFlow кладёт XML в папку, 1С их забирает регламентным
  заданием или по кнопке. HTTP-сервис на файловой базе не поднять, поэтому обмен файлами.

## Как это работает со стороны DocFlow

Оператор/бухгалтер загружает скан → DocFlow распознаёт → подтверждённый документ
выгружается XML-файлом в папку обмена (`ONEC_FILE_DIR`, по умолчанию
`/var/lib/docflow/onec_outbox`). Один документ = один файл. Запись атомарная
(сначала `.имя.xml`, затем переименование), так что 1С не прочитает недописанный файл.

Имя файла: `<SourceId>_<kind>.xml`, например
`7a1c3e64-2b8d-4a1e-9c11-0f2a5b6d7e80_create.xml`. Начинается с `<SourceId>` —
документ в папке обмена и запись в 1С сводятся по имени файла напрямую, без
расшифровки таймстампа. Суффикс `kind` (`create` / `partial` / `update`) не
даёт повторной выгрузке одного документа перезаписать на диске ещё не
забранный файл предыдущей — например, `partial`, за которым вскоре следует
`update`, когда клиент дозаполнил поля.

## Виды выгрузки (атрибут `kind`) — ключевой момент

Один и тот же документ может прийти несколько раз. Сопоставление — по `<SourceId>`
(это стабильный UUID документа в DocFlow). 1С должна работать по принципу **upsert**:
найти документ по SourceId → если нет, создать; если есть, обновить.

| `kind` | Когда приходит | Что делать в 1С |
|---|---|---|
| `create` | Документ распознан полностью | Создать/обновить документ со всеми полями |
| `partial` | Распознано частично (атрибут `incomplete="true"`) | Создать/обновить тем, что есть; пометить как требующий проверки; ждать `update` |
| `update` | Пользователь вручную дозаполнил недостающие поля | Найти документ по SourceId и дополнить недостающие поля |

`<MissingFields>` в режиме `partial` перечисляет, каких реквизитов ещё нет —
удобно подсветить их в 1С как незаполненные.

## Формат XML

Пример полного документа (`kind="create"`):

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Message format="EnterpriseData/1.0">
  <Body>
    <Document kind="create">
      <SourceId>7a1c3e64-2b8d-4a1e-9c11-0f2a5b6d7e80</SourceId>
      <Type>schet_faktura</Type>
      <TypeTitle>Счёт-фактура (ЭСЧФ)</TypeTitle>
      <Target object="Документ.СчетФактураПолученный" kind="document"/>
      <Number>ЭСЧФ-000451</Number>
      <Date>05.07.2026</Date>
      <Total>3540.00</Total>
      <Currency>BYN</Currency>
      <Organization>ЧУП "ПартнёрБухгалтер"</Organization>
      <FileName>scan.jpg</FileName>
      <Counterparty>
        <Name>ООО "Ромашка"</Name>
        <UNP>191234567</UNP>
      </Counterparty>
      <Lines>
        <Line>
          <Name>Бумага А4 500 л.</Name>
          <Qty>10</Qty>
          <Unit>пач</Unit>
          <Price>295.00</Price>
          <Amount>2950.00</Amount>
          <VAT>20%</VAT>
        </Line>
        <Line>
          <Name>Тонер HP 26A</Name>
          <Qty>1</Qty>
          <Unit>шт</Unit>
          <Price>590.00</Price>
          <Amount>590.00</Amount>
          <VAT>20%</VAT>
        </Line>
      </Lines>
      <MissingFields></MissingFields>
      <AdditionalFields></AdditionalFields>
    </Document>
  </Body>
</Message>
```

Пример частичной выгрузки (`kind="partial"`, не хватает суммы и УНП):

```xml
<Document kind="partial" incomplete="true">
  <SourceId>7a1c3e64-2b8d-4a1e-9c11-0f2a5b6d7e80</SourceId>
  <Type>schet_faktura</Type>
  <Number>ЭСЧФ-000451</Number>
  <Date>05.07.2026</Date>
  <Organization>ЧУП "ПартнёрБухгалтер"</Organization>
  <Counterparty><Name>ООО "Ромашка"</Name></Counterparty>
  <Lines></Lines>
  <MissingFields>
    <Field>total</Field>
    <Field>unp</Field>
  </MissingFields>
</Document>
```

Готовые эталонные файлы (`create.xml`, `partial.xml`, `update.xml`) — приложены
отдельно к передаче; их можно скормить приёмнику как тест.

## Папки юрлиц (изменение от 08.2026)

Каждое юрлицо получает **свою папку** внутри каталога обмена, и выгрузки в ней не
смешиваются с чужими:

```
onec_outbox/
  191234567/        ← папка компании А (имя = УНП либо заданное администратором)
    <SourceId>_<kind>.xml
  200111222/        ← папка компании Б
  archive/          ← отработанные файлы, разложенные по месяцам и папкам компаний
```

Документы, не привязанные ни к какому юрлицу (загруженные до этой доработки),
по-прежнему ложатся в корень каталога — обработку менять не нужно.

Реквизиты компании продублированы внутри XML, чтобы приёмник не зависел от имени
папки:

```xml
<Company>
  <Name>ЧУП "Василёк"</Name>
  <UNP>200111222</UNP>
  <Folder>200111222</Folder>
</Company>
```

## Табличная часть: элемент `Table` (изменение от 08.2026)

`<Lines>` остаётся как был — ломать уже написанный приёмник не нужно. Рядом
добавлен `<Table>`: та же табличная часть, но со **структурой колонок**. DocFlow
теперь восстанавливает таблицу по координатам слов на странице, поэтому известно,
какая ячейка какой колонке принадлежит, и гадать по порядку чисел не приходится.

```xml
<Table source="layout" rows="2">
  <Columns>
    <Column index="1" role="index">№</Column>
    <Column index="2" role="name">Наименование товара</Column>
    <Column index="3" role="qty">Кол-во</Column>
    <Column index="4" role="unit">Ед.</Column>
    <Column index="5" role="price">Цена</Column>
    <Column index="6" role="amount">Сумма</Column>
  </Columns>
  <Rows>
    <Row index="1">
      <Cell column="1" role="index">1</Cell>
      <Cell column="2" role="name">Бумага офисная А4</Cell>
      <Cell column="3" role="qty">10</Cell>
      <Cell column="4" role="unit">шт</Cell>
      <Cell column="5" role="price">12.50</Cell>
      <Cell column="6" role="amount">125.00</Cell>
    </Row>
  </Rows>
  <TotalsRow>
    <Cell column="6" role="amount">315.00</Cell>
  </TotalsRow>
</Table>
```

- `role` — назначение колонки: `name`, `qty`, `unit`, `price`, `amount`, `vat`,
  `index` (служебный номер строки), `other` (колонка документа, которой нет
  соответствия — её содержимое передаётся как есть).
- `source` — чем разобрана таблица: `layout` (по координатам на странице, самый
  надёжный), `rules` (по шапке в тексте), `model` (локальной моделью).
- `TotalsRow` — строка «Итого» из самой таблицы, отделённая от позиций. В сумму
  документа она не входит дважды: итог документа по-прежнему в `<Total>`.
- `Title` колонки — подпись **как она напечатана в документе**. Сопоставлять
  колонки надёжнее по `role`, а `Title` показывать пользователю.

Рекомендация приёмнику: если `<Table>` есть — разбирать его, `<Lines>` в этом
случае содержит то же самое в плоском виде. Если `<Table>` нет — работать по
`<Lines>`, как раньше.

`<AdditionalFields>` теперь содержит только реквизиты: обрывки распознанного
текста (длинные значения, куски строк таблицы) туда больше не попадают.

## Соответствие полей реквизитам «Моей бухгалтерии 8»

Имена реквизитов взяты из конфигурации заказчика (документы СчётФактураПолученный/ЭСЧФ,
СчётНаОплату; справочники Контрагенты, Организации).

### Шапка

| Элемент XML | Реквизит документа 1С | Примечание |
|---|---|---|
| `SourceId` | доп. реквизит (расширение) «ИдентификаторDocFlow» | ключ сопоставления, обязательно хранить |
| `Number` | Номер | стандартный реквизит документа |
| `Date` | Дата | стандартный реквизит документа |
| `Type` | — | код вида документа в DocFlow |
| `TypeTitle` | — | то же название по-русски, для журналов и сообщений |
| `Target/@object` | **объект метаданных, который нужно создать** | напр. `Документ.ПоступлениеТоваровУслуг`; согласовывается заранее, см. ниже |
| `Target/@kind` | — | `document` / `catalog` / `file` — документ, элемент справочника или только присоединённый файл |
| `Total` | СуммаТовара / СуммаВсего | число |
| `VATAmount` | СуммаНДС | сумма НДС по документу, число (не ставка) |
| `Currency` | Валюта | ссылка на справочник Валюты (по коду, напр. BYN) |
| `Organization` | Организация | наименование получателя документа (покупатель/плательщик) |
| `OrganizationUNP` | Организация.УНП | **ключ поиска своей организации** |
| `Counterparty/Name` | Контрагент.Наименование | для поиска/создания |
| `Counterparty/UNP` | Контрагент.УНП | **ключ поиска контрагента** |
| `FileName` | — | имя исходного скана (для справки) |

Номер и дата договора-основания (если распознаны в тексте документа) уходят
не отдельными элементами шапки, а через `<AdditionalFields>`: `contract_number`
и `contract_date`. Раньше не извлекались вовсе — в 1С не попадали ни в каком виде.

### Табличная часть (`Lines/Line`)

| Элемент XML | Колонка табличной части |
|---|---|
| `Name` | Номенклатура (поиск/создание в справочнике Номенклатура) |
| `Qty` | Количество |
| `Unit` | ЕдиницаИзмерения |
| `Price` | Цена |
| `Amount` | Сумма |
| `VAT` | СтавкаНДС |

Табличная часть распознаётся двумя способами: по строке-шапке таблицы
(«Наименование | Кол-во | Ед. | Цена | Сумма») с раскладкой значений по
колонкам, а для незнакомых форм — локальной моделью. Перед выгрузкой сумма по
строкам сверяется с `Total` (допуск 1%).

Если сверка не прошла или часть строк осталась без суммы, позиции в 1С **не
отправляются**: лучше документ без номенклатуры, чем с неверными суммами.
Документ при этом **не задерживается** — шапка уходит в 1С в обычном порядке,
а в выгрузке появляется `<MissingFields><Field>lines</Field></MissingFields>` и
`incomplete="true"`. Позиции сотрудник вносит в 1С руками.

Итого в `<Lines>` приходят либо сошедшиеся строки, либо пусто, но никогда —
разъехавшаяся таблица.

## Куда класть документ: элемент `<Target>`

Раньше приёмник должен был сам решать, во что превращать код из `<Type>`.
Теперь это решение принято заранее и приезжает вместе с документом.

`<Target object="..." kind="..."/>` — полное имя объекта метаданных вашей
конфигурации, в который документ нужно записать. Приёмнику остаётся выполнить
то, что сказано, а не поддерживать собственную таблицу соответствий:

| `kind` | Что делать |
|---|---|
| `document` | создать документ указанного вида |
| `catalog` | создать/обновить элемент справочника |
| `file` | не создавать учётный объект, приложить скан как присоединённый файл |

Соответствие «тип документа → объект 1С» хранится на стороне DocFlow в файле
`doctypes.json` и меняется без пересборки — достаточно перезапустить сервис.
**Заполняется он по вашей базе:** имена берутся из дерева метаданных
(Конфигуратор → Документы / Справочники) и должны совпадать посимвольно.
Заготовка со всеми известными типами — `doctypes.example.json`.

Если для типа объект-приёмник не задан, документ **не выгружается вообще**:
он остаётся в DocFlow на проверке у оператора. Это сделано намеренно — лучше
задержать документ, чем создать его не в том разделе учёта. Появился новый вид
документа — добавьте ему строку в `doctypes.json`, и поток пойдёт сам.

Список текущих типов и их маппинга всегда доступен: `GET /api/doctypes`.

`<Type>` остаётся в выгрузке для журналов и обратной совместимости:
`schet_faktura` (счёт-фактура/ЭСЧФ), `invoice` (счёт на оплату), `waybill`
(накладная ТТН-1/ТН-2), `upd`, `act` (акт выполненных работ), `act_priemki`
(акт приёмки-передачи), `act_sverki` (акт сверки), `receipt` (чек), `contract`
(договор), `payment_order` (платёжное поручение), `power_of_attorney`
(доверенность). Перечень открыт и пополняется.

## Режим загрузки: кнопка, а не расписание

База файловая и живёт на рабочей станции (`D:\1c8_bases\Локация-2`). Регламентное
задание в файловом режиме выполняется только пока у пользователя открыта 1С —
то есть «автоматика», которая молча стоит по вечерам и выходным. Поэтому загрузка
сделана **ручной**: обработка с кнопкой «Загрузить документы».

Как это работает:

1. DocFlow пишет XML в папку обмена (сетевая шара на сервере DocFlow либо
   каталог, доступный станции по UNC-пути).
2. Бухгалтер нажимает кнопку — обработка читает все новые файлы за один проход и
   показывает протокол: сколько загружено, что требует проверки, где ошибки.
3. Обработанные файлы переносятся в подпапку архива, поэтому повторное нажатие
   ничего не дублирует. Плюс страховка на уровне данных — upsert по `SourceId`.

Каркас обработки лежит в `onec-receiver/ЗагрузкаDocFlow.bsl`: разбор XML, обход
папки, идемпотентность и возврат статуса написаны и от конфигурации не зависят.
Незаполненной оставлена процедура `ЗаполнитьДокумент` — это ровно та часть,
которой нужны точные имена объектов и реквизитов базы.

## Что нужно сделать в 1С (задачи приёмника)

1. **Расширение конфигурации** с обработкой «Загрузка DocFlow» (кнопка).
   Типовая на поддержке — править её нельзя, только расширением.
2. **Разбор XML** и создание объекта, указанного в `<Target>` (не собственная
   таблица соответствий по `<Type>` — маршрут уже согласован на стороне DocFlow).
3. **Контрагент по УНП:** искать в справочнике Контрагенты по `Counterparty/UNP`.
   Если не найден — создать (Наименование = `Counterparty/Name`, УНП = `Counterparty/UNP`).
4. **Организация:** найти по `Organization` (наименование или УНП своей фирмы).
5. **Номенклатура строк:** по `Line/Name` искать в справочнике Номенклатура,
   при отсутствии — создавать или складывать в «нераспознанную» для ручной привязки.
6. **Upsert по SourceId:** хранить `SourceId` в доп. реквизите документа.
   `create`/`partial` — найти по SourceId или создать; `update` — найти по SourceId и дополнить.
7. **Частичные документы** (`incomplete="true"`) — создавать непроведёнными и помечать,
   что нужна проверка; поля из `<MissingFields>` подсветить.
8. **Идемпотентность:** повторный файл с тем же SourceId не должен создавать дубль.
   Обработанные файлы переносить в архивную подпапку (или удалять).
9. **Доступ к папке обмена:** станция должна видеть каталог `ONEC_FILE_DIR`
   сервера DocFlow по сети (SMB-шара или примонтированный диск). Права —
   чтение и удаление/перенос файлов.

## Обратная связь по статусу (опционально, желательно)

Сейчас поток односторонний (DocFlow → 1С). Если нужно возвращать статус обратно
в приложение (проведён / отклонён), DocFlow готов принять его двумя способами —
согласуем отдельно:
- REST-режим: DocFlow может слать в HTTP-сервис 1С и принимать ответ;
- файловый: 1С кладёт файл-квитанцию с `SourceId` и статусом в отдельную папку,
  DocFlow её разбирает.

## Соответствие типов объектам базы (сверено по отчёту по конфигурации)

База: «Моя бухгалтерия 8» 8.26.05.01.3, платформа 8.3.24.1819, файловый режим,
`D:\1c8_bases\Локация-2`, конфигурация на поддержке. Имена ниже взяты из отчёта
по конфигурации от 20.07.2026, а не подобраны по аналогии с 1С:Бухгалтерией.

| Тип DocFlow | Объект 1С | Табличная часть |
|---|---|---|
| `waybill` — ТТН-1 / ТН-2 | `Документ.ПоступлениеТМЦ` | `Номенклатура` |
| `act` — акт выполненных работ | `Документ.ПолучениеУслуг` | `Услуги` |
| `schet_faktura` — ЭСЧФ | `Документ.ЭСЧФВходящий` | `Номенклатура` |
| `act_priemki` — акт приёмки ТМЦ | `Документ.АктПриемкиТМЦПриход` | `Номенклатура` |
| `contract` — договор | `Справочник.Договора` | — |
| `power_of_attorney` — доверенность | `Документ.Доверенность` | — |

Главная особенность этой конфигурации: **у документов прихода нет отдельного
реквизита «Контрагент»**. Поставщик хранится как субконто счёта кредита —
`СчетКредита` + `КСубконто1..3` с типом «ЛюбаяСсылка». Поэтому счёт расчётов с
поставщиками и номер субконто вынесены в константы расширения
(`DocFlowСчетРасчетовСПоставщиками`), а не зашиты в код: порядок субконто
зависит от настройки плана счетов у заказчика.

Исключение — `Документ.ЭСЧФВходящий`: там `Контрагент`, `УНППоставщика` и
`НаименованиеПоставщика` лежат прямо в шапке, поэтому этот вид заполняется
точнее остальных.

Контрагент ищется **только по УНП**. По наименованию не ищем: после OCR
«ООО Ромашка» и «ООО "Ромашка"» — разные строки, и поиск по имени плодит дубли
вместо связывания. Не найден по УНП — создаётся новый с `ФлагПоставщик`.

## Что осталось нерешённым (вопросы к бухгалтерии, а не к базе)

Эти типы в реестре с пустым `object` и в 1С не уходят:

- **Счёт на оплату входящий.** Все три `СчетНаОплату*` (ТМЦ, Блюд,
  РозницаОбщепит) — исходящие, наши покупателям. Входящего счёта поставщика в
  конфигурации нет; ближайший кандидат — `Документ.ЗаказПоставщику`. Нужен ли
  этот тип вообще?
- **Чек.** `Документ.АвансовыйОтчет` есть, но чек сам по себе документа не
  образует — он строка авансового отчёта. Как оформляем?
- **Платёжное поручение.** `Документ.ПлатежноеПоручение` есть, но платёжки
  приходят из клиент-банка, а не сканами. Принимаем ли их вообще?
- **Акт сверки.** Ни документа, ни справочника присоединённых файлов в
  конфигурации нет. Складывать некуда.
- **УПД** — российская форма, в белорусской базе не нужна.

Плюс одно техническое подтверждение перед боевым запуском: **какой счёт и какое
по счёту субконто** отведены под контрагента в расчётах с поставщиками.

## Что нужно согласовать один раз (чек-лист)

Чтобы заполнить `doctypes.json`, нужен ответ по каждому виду документа,
который реально приходит от клиентов:

1. В какой объект базы он должен попадать — документ, справочник или только
   присоединённый файл? Точное имя из метаданных.
2. Какие реквизиты для этого вида обязательны, чтобы документ считался готовым
   к проведению (без них DocFlow отправит частичную выгрузку и попросит
   сотрудника дозаполнить).
3. Нужна ли табличная часть (номенклатура) или достаточно шапки.
4. Что делать с видами, которые в учёте не отражаются (доверенности, акты
   сверки) — прикладывать файлом к контрагенту или не принимать вовсе.

Первые три пункта по большинству видов снимаются просмотром базы, четвёртый —
вопрос учётной политики, его подтверждает бухгалтерия.

## Контакты по формату

Со стороны DocFlow формат стабильный. Если для приёмника удобнее другие имена
элементов или структура (например, обёртка EnterpriseData 1.х «как в типовой»),
это правится на нашей стороне — присылайте требования.

## Возврат статуса в DocFlow (обязательно)

После обработки выгрузки 1С сообщает результат обратно. Без этого пользователь
видит только «передано в обмен» и не знает, дошёл документ до учёта или нет.

```
POST https://<домен>/api/onec/status
X-DocFlow-Token: <ONEC_INBOUND_TOKEN из .env сервера>
Content-Type: application/json

{
  "source_id": "11111111-2222-3333-4444-555555555555",
  "status":    "posted",
  "ref":       "Счёт на оплату 145 от 12.03.2026",
  "message":   ""
}
```

`source_id` — тот же `SourceId`, что пришёл в выгрузке. Допустимые значения
`status`:

| Значение | Когда отправлять |
|---|---|
| `accepted` | документ создан в 1С, но ещё не проведён |
| `posted` | документ проведён |
| `rejected` | документ отклонён (в `message` — причина для пользователя) |
| `error` | ошибка обработки (в `message` — текст ошибки) |

Ответы: `200` — принято, `401` — неверный токен, `404` — документ с таким
`source_id` не найден, `400` — недопустимый статус.

Вызов идемпотентен: повторная отправка того же статуса безопасна. При
`rejected` и `error` пользователю уходит push с текстом из `message` — пишите
туда то, что человек сможет исправить.

Если 1С молчит дольше `ONEC_ACK_TIMEOUT` (по умолчанию 6 часов), DocFlow пишет
предупреждение в лог с количеством неподтверждённых документов. Это и есть
сигнал, что обмен встал.
