# Приёмка и передача

Документ для сдачи работы. Разделён на три части: что проверяется автоматически,
что показывается заказчику руками и что остаётся за периметром поставки.

Последнее — не оговорки задним числом, а вещи, которые физически нельзя
выполнить со стороны подрядчика: они требуют учётных записей, документов и
специалистов заказчика. Их нужно подписать вместе с остальным.

---

## 1. Установка

На чистом сервере (Ubuntu 22.04+, Docker Engine, 8 ГБ ОЗУ):

```bash
git clone <репозиторий> docflow-deploy && cd docflow-deploy
./deploy.sh
```

Скрипт спросит домен и дальше сделает всё сам: сгенерирует все секреты
(включая пароль базы и токен для 1С), поднимет стек, включит HTTPS с
автоматическим сертификатом Let's Encrypt и покажет пароль администратора.

Неинтерактивно:

```bash
DOMAIN=docs.klient.by ACME_EMAIL=it@klient.by ./deploy.sh
```

Единственное, что нужно подготовить заранее: домен с A-записью на этот сервер и
открытые порты 80 и 443.

---

## 2. Автоматические проверки

```bash
./smoke-test.sh
```

Проверяет доступность, HTTPS и редирект с HTTP, вход и отказ при неверном
пароле, недоступность API без токена, разделение по ролям, блокировку перебора
паролей, требование текущего пароля при смене, отказ от слабых паролей, работу
канала приёма статусов из 1С, отсутствие секретов из примера в конфигурации,
наличие резервных копий.

Код возврата 0 — все проверки пройдены.

Отдельно — проверка восстановимости резервной копии:

```bash
./backup.sh
./verify-backup.sh backups/<последняя>
```

Второй скрипт поднимает одноразовую базу, восстанавливает в неё дамп,
расшифровывает файлы текущим ключом и сверяет контрольные суммы. Боевой стенд
при этом не затрагивается.

---

## 3. Проверки при заказчике

Автоматика не покажет главного — что системой можно пользоваться. Это
демонстрируется вживую:

1. **Загрузка с телефона.** Снять документ камерой, обрезать и выровнять
   контраст, отправить. Проверить, что дошло.
2. **Работа без сети.** Включить авиарежим, снять документ, выключить
   авиарежим — документ должен уйти сам.
3. **Полное распознавание.** Документ с чёткими реквизитами уходит в 1С без
   участия оператора.
4. **Частичное распознавание.** Документ, где не читается часть реквизитов:
   распознанное уходит в 1С сразу, сотрудник дозаполняет остальное, дополнение
   доходит до того же документа в 1С.
5. **Возврат статуса.** 1С сообщает о проведении — статус виден в приложении и
   приходит уведомлением.
6. **Разделение доступа.** Клиент видит только свои документы, оператор — все,
   администратор — ещё и пользователей с журналом.
7. **Блокировка сотрудника.** Заблокированный пользователь теряет доступ
   немедленно, не дожидаясь истечения сессии.

## 4. Точность распознавания

ТЗ требует согласованного уровня точности на тестовой выборке. Подтвердить это
можно только на реальных документах заказчика, поэтому замер выполняется так:

1. Заказчик передаёт 30–50 типичных документов (счета, накладные, акты, чеки).
2. К каждому прикладывается json с верными значениями:

```json
{ "doc_type": "invoice", "number": "145", "date": "12.03.2026",
  "total": "375.00", "unp": "191234567" }
```

3. Запуск:

```bash
docker compose cp ./samples docflow-backend:/samples
docker compose exec docflow-backend /app/accuracy -dir /samples
```

На выходе — таблица точности по каждому реквизиту. **Эта таблица и есть
согласованный уровень**: её распечатывают, подписывают и прикладывают к акту.

Отдельно смотрите столбец «неверно». Пустое поле сотрудник заполнит; поле,
распознанное неправильно, он проведёт как есть. Система намеренно помечает
неуверенные значения как отсутствующие, чтобы их увидел человек, — поэтому
«пусто» здесь безопаснее, чем «неверно», и оценивать нужно именно второе.

## 5. Что остаётся за периметром поставки

Ниже — работы, которые нельзя выполнить со стороны подрядчика. Их следует либо
заказать отдельно, либо принять как зону ответственности заказчика.

### 5.1. Приёмник на стороне 1С

DocFlow формирует XML и складывает его в каталог обмена (или отправляет по
REST). Разбор этого XML и создание документов в 1С пишет 1С-специалист
заказчика. Полное техническое задание для него — в `ONEC-INTEGRATION.md`,
включая формат, маппинг полей, идемпотентность и возврат статуса.

**Важно:** формат выгрузки — собственная схема DocFlow, а не стандартный
EnterpriseData, несмотря на историческое название атрибута. Штатный механизм
обмена 1С её не прочитает, разбор нужно написать. Это решение принято ради
простоты приёмника; если заказчику нужен именно EnterpriseData, это отдельная
работа.

### 5.2. Согласование состава реквизитов

Система извлекает: тип документа, номер, дату, сумму, сумму НДС, валюту,
контрагента с налоговым номером, собственную организацию, табличную часть.
Достаточен ли этот набор для проведения документа в конкретной конфигурации
«Моя бухгалтерия 8» — знает только 1С-специалист заказчика. Пример XML в
`ONEC-INTEGRATION.md`; согласование состава реквизитов нужно провести до
опытной эксплуатации.

Известные ограничения: одна ставка НДС на документ (документ с 10% и 20%
свернётся в одно значение); договор-основание не извлекается отдельным полем.

### 5.3. Публикация мобильного приложения

Нативные проекты Android и iOS собраны и лежат в репозитории, разрешения и
минимальные версии ОС настроены. Публикация требует учётных записей
разработчика **заказчика** (Google Play, Apple Developer), его политики
конфиденциальности и его же решения — публичные сторы или закрытое
корпоративное распространение. Подробно — в `MOBILE.md`.

Приложение работает с персональными данными, поэтому выпускать его под
аккаунтом подрядчика некорректно.

### 5.4. Вход по SMS

В ТЗ помечен как требующий уточнения. Не реализован: требует выбора и оплаты
провайдера рассылки заказчиком. Сейчас вход по логину и паролю.

### 5.5. Обязанности оператора персональных данных

Заказчик находится в Беларуси, применяется Закон РБ от 07.05.2021 № 99-З.
Технические меры реализованы (шифрование файлов, разделение доступа, журнал
действий, данные не покидают инфраструктуру заказчика). Организационные меры —
назначение ответственного, согласия субъектов, политика обработки, сроки
хранения — на стороне заказчика. Подробно в `README-DEPLOY.md`.

### 5.6. Эксплуатация

Резервное копирование настроено скриптами, но расписание cron и вывоз копий на
отдельный носитель настраивает администратор заказчика: копия на том же диске
не спасает от отказа диска. Рекомендуемое расписание — в `README-DEPLOY.md`.

---

## 6. Передача секретов

Передаются отдельно от репозитория и от резервных копий:

| Секрет | Последствия потери |
|---|---|
| `FILES_ENCRYPTION_KEY` | все документы **безвозвратно** нечитаемы |
| `JWT_SECRET` | потребуется повторный вход всех пользователей |
| `POSTGRES_PASSWORD` | доступ к базе только через контейнер |
| `ONEC_INBOUND_TOKEN` | 1С не сможет вернуть статус, выпускается новый |
| пароль администратора | сбрасывается другим администратором |
| ключ подписи Android | **нельзя обновить** приложение в Google Play |

Невосстановимы только два: ключ шифрования файлов и ключ подписи Android.
Оба хранятся у заказчика в менеджере паролей и в бумажной копии.

Пароль администратора, выданный при установке, система требует сменить при
первом входе — до смены она не пускает дальше этого экрана.
